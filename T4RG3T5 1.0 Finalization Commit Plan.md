# T4RG3T5 1.0 Finalization Commit Plan

Project: T4RG3T5
Starting point: 0.6
Release path: 0.7.0-rc1 → testing → 1.0.0

This plan follows `T4RG3T5 1.0 Finalization Design Bible.md`. The objective is to harden the existing targeting and lock-camera implementation without adding new gameplay systems, generalized frameworks, or CHIM-specific mechanics.

Each implementation commit is completed and validated independently. Review happens after every commit. Runtime findings during RC testing become separate, focused fix commits rather than an omnibus cleanup commit.

## Worktree rule

The repository is already dirty. Existing changes outside the deliberate T4RG3T5 commit are not part of this plan and must not be staged, reverted, or rewritten. The design bible and unrelated assets/tooling remain separate unless explicitly requested.

The current T4RG3T5 ESP already contains the required Lua script declarations. Do not add an `.omwscripts` manifest or alter the plugin structure unless inspection proves that the release artifact requires it.

### 2. `REFACTOR: Centralize target lifecycle`

File:

- `content/t4rg3t5/scripts/s3/target/lockOnManager.lua`

Changes:

- Make `state.targetObject` the authoritative semantic lock state.
- Consolidate target changes around `setTarget` and `clearTarget`.
- Gate input, acquisition, switching, tracking, and combat auto-lock on `TargetLockToggle`.
- Clear target, marker, camera ownership, and temporary state when targeting is disabled.
- Initialize target validity, height metadata, and health before initializing camera state.
- Remove semantic decisions based on marker visibility.
- Preserve `S3TargetLockOnto` and the legacy `Manager` surface.
- Keep target objects out of persistent storage and save data.

Validation:

- LuaJIT syntax check.
- OpenMW context, engine-handler, event-bus, lifecycle, and storage checks.
- Manual lifecycle review for acquire, switch, unlock, death, invalid objects, sheathing, and disable-while-locked.

### 3. `FIX: Make lock loss explicit`

File:

- `content/t4rg3t5/scripts/s3/target/lockOnManager.lua`

Changes:

- Add a short invalid-tracking grace timer, initially about `0.25` seconds.
- Apply grace to temporary offscreen, occlusion, and tracking-envelope failures.
- Unlock immediately for invalid objects, death where applicable, manual unlock, disabled targeting, categorical ineligibility, and lifecycle teardown.
- Reset the grace timer when target validity returns.
- Correct LOS semantics: no hit and target-first hit are clear; another first hit is blocked.
- Keep one basic acquisition LOS test regardless of `CheckLOS`.
- Use `CheckLOS` only for continuous post-lock enforcement.

Validation:

- LuaJIT syntax check.
- Event lifecycle, event-bus, and lifecycle checks.
- Runtime tests for temporary and sustained offscreen/occlusion, target return before and after grace, death, deletion, range loss, and manual unlock.

### 4. `REFACTOR: Isolate lock-camera ownership`

File:

- `content/t4rg3t5/scripts/s3/target/lockOnManager.lua`

Changes:

- Organize camera ownership around `beginLockCamera`, `updateLockCamera`, and `endLockCamera` or the closest compatible structure.
- Make `ThirdPersonLockCamera` independent from semantic targeting.
- When disabled, preserve target acquisition, switching, marker presentation, and applicable facing behavior without acquiring Static camera mode.
- Release mode control only through the convergent teardown path.
- Restore only camera state explicitly captured by T4RG3T5 and only while ownership remains valid.
- Reset spring velocities, shoulder state, and temporary camera data on exit.
- Fall back to normal camera behavior without destroying a valid target.

Validation:

- LuaJIT syntax, context, interface, and lifecycle checks.
- Runtime tests with the camera enabled and disabled, including toggling while locked, first-person/third-person transitions, menu transitions, and another camera owner.

### 5. `FIX: Use analytical camera springs`

File:

- `content/t4rg3t5/scripts/s3/target/lockOnManager.lua`

Changes:

- Replace Euler integration with the analytical critically damped spring from the design bible.
- Handle zero and negative `dt` safely.
- Permit only a defensive cap for absurd application-resume or debugger time steps.
- Apply the same stable integration to camera position and look-target position.
- Preserve existing responsiveness settings as closely as practical.

Validation:

- Standalone numerical comparison at 30, 60, 120/144, and 240 FPS over equal elapsed time.
- LuaJIT syntax check.
- Lua hot-path budget check.
- Runtime checks for hitches, settling, and absence of overshoot caused by frame rate.

### 6. `FIX: Collision-test final camera candidates`

File:

- `content/t4rg3t5/scripts/s3/target/lockOnManager.lua`

Changes:

- Construct each complete shoulder camera candidate before collision testing.
- Raycast from the orbit pivot to the actual candidate position.
- Clamp obstructed candidates toward the hit point and apply a collision skin.
- Ensure backward distance, vertical offset, and shoulder offset are all represented in the tested vector.
- Keep any center-line ray as a preliminary optimization only.
- Prevent `CameraMinDistance` from pushing the final camera through geometry.
- Keep the implementation narrow; do not create a generalized camera framework.

Validation:

- LuaJIT syntax check.
- Lua hot-path budget check.
- Runtime obstruction matrix: exterior, corridor, doorway, corner, pillar, stairs, slope, low ceiling, wall-adjacent target, and player against a wall.

### 7. `FIX: Add persistent shoulder hysteresis`

File:

- `content/t4rg3t5/scripts/s3/target/lockOnManager.lua`

Changes:

- Add persistent `cameraSide`, defaulting to the right shoulder for a new camera session.
- Evaluate corrected current and alternate shoulder candidates.
- Retain the current side until it falls below the BAD threshold.
- Switch only when the alternate side reaches the higher GOOD threshold.
- Reset shoulder state when an independent lock-camera session begins.
- Avoid stale shoulder state persisting indefinitely between unrelated sessions.

Validation:

- Runtime tests with alternating obstructions, one-sided obstruction, both sides blocked, target switching, unlock/relock, and frame-by-frame oscillation pressure.

### 8. `FIX: Convert motion and hit bounce to time`

File:

- `content/t4rg3t5/scripts/s3/target/lockOnManager.lua`

Changes:

- Convert first-person tracking and player-facing interpolation to timestep-based behavior.
- Express angular response through exponential interpolation or degrees/radians per second.
- Convert hit-marker bounce to elapsed-time animation, approximately `0.15` seconds.
- Audit camera transitions and remaining visible frame-count increments.
- Preserve physical mouse-distance flick switching; it is input distance, not temporal animation.

Validation:

- LuaJIT syntax check.
- Lua hot-path budget check.
- Runtime comparison of tracking, facing, transitions, and bounce duration across the frame-rate matrix.

## RC testing and follow-up commits

After Commit 12, run the complete design-bible matrix:

- 30/60/120-144/200+ FPS behavior.
- Camera obstruction and target-size cases.
- Target lifecycle and grace-period cases.
- Repeated input and camera ownership transitions.
- Crosshair and UI coexistence.
- CHIM present/absent interoperability.

Every regression found during RC testing gets a separate focused commit named for the violated contract. Do not redesign the product or bundle unrelated fixes.

### Final release commit

`VERSION: T4RG3T5 1.0.0`

Update release metadata only after the RC matrix passes and no known major camera, lifecycle, timing, or API defects remain. Run the final package, plugin, content-reference, syntax, context, interface, and documentation checks before release.

## Explicit non-goals

Do not add:

- New targeting modes or target-priority systems.
- Boss-specific behavior, target prediction, or aim assistance.
- Camera presets, cinematic cameras, or camera frameworks.
- Generalized event infrastructure.
- CHIM combat coupling.
- Extra tuning settings for internal implementation details.
- Speculative optimization without a measured problem.
